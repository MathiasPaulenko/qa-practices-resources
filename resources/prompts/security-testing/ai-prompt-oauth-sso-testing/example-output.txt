OAUTH-001
Category: Auth Code
Scenario Name: Authorization code flow with PKCE succeeds
Flow: Authorization Code + PKCE
Preconditions: Registered SPA client with redirect URI https://app.secureapp.io/callback; test user user1@secureapp.io exists.
Test Steps:
1. GET /authorize?client_id=spa-client&redirect_uri=https%3A%2F%2Fapp.secureapp.io%2Fcallback&response_type=code&scope=openid%20profile&state=abc123&code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM&code_challenge_method=S256
2. Log in as the test user and consent.
3. Follow the redirect back to the client and capture the code.
4. POST /token with grant_type=authorization_code, code, redirect_uri and code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk
Expected Result: HTTP 200 with access_token (JWT, 15 min), refresh_token (opaque) and id_token.
Security Implication: Confirms PKCE binds the code to the verifier and blocks interception.
Test Data: client_id=spa-client, state=abc123.
Cleanup: Revoke the refresh token via /revoke.
Priority: Critical
Automation Possible: Yes - API

OAUTH-002
Category: Security
Scenario Name: State parameter CSRF attack is rejected
Flow: Authorization Code
Preconditions: Attacker starts an authorization request that sets state=evil-state; the victim browser completes login and returns with the attacker's code.
Test Steps:
1. Initiate login on the victim client with state=legit-xyz stored in session.
2. Inject a callback carrying state=evil-state with a valid code.
3. Let the client validate the callback.
Expected Result: The client rejects the callback before exchanging the code; no tokens issued.
Security Implication: A missing or mismatched state check lets an attacker bind their session to the victim's account.
Test Data: state=legit-xyz vs state=evil-state.
Cleanup: Clear the session cookie.
Priority: Critical
Automation Possible: Yes - Playwright

OAUTH-003
Category: Token
Scenario Name: Refresh token rotation invalidates the old token
Flow: Refresh Token
Preconditions: Active session with rotating refresh token rt-1.
Test Steps:
1. POST /token with grant_type=refresh_token and rt-1.
2. Capture the new pair (access-token-2, rt-2).
3. Replay POST /token with the old rt-1.
Expected Result: First request returns 200; replay with rt-1 returns 400 invalid_grant and the whole token family is revoked.
Security Implication: Reuse detection stops a stolen refresh token from being replayed.
Test Data: refresh_token=rt-1.
Cleanup: Revoke rt-2 and all sessions.
Priority: Critical
Automation Possible: Yes - API

OAUTH-004
Category: SSO
Scenario Name: Email conflict when linking a second provider
Flow: Multi-provider account linking
Preconditions: Local account exists with user@corp.io linked to GitHub; user attempts to link a Google account with the same email.
Test Steps:
1. Sign in with GitHub (user@corp.io).
2. From account settings, choose "Link Google" and complete Google consent for user@corp.io.
Expected Result: Google is linked to the same account — or, if policy forbids auto-linking, a conflict warning is shown and no silent merge happens.
Security Implication: Wrong auto-link logic can attach a stranger's identity to an account.
Test Data: GitHub user@corp.io, Google user@corp.io.
Cleanup: Unlink Google; keep the GitHub link.
Priority: High
Automation Possible: Yes - Playwright

OAUTH-005
Category: Session
Scenario Name: Global logout revokes all sessions
Flow: OIDC back-channel logout
Preconditions: The same user has active sessions on desktop Chrome, mobile app and a second browser.
Test Steps:
1. Trigger "Sign out of all devices" from the desktop session.
2. Call a protected API with the access/refresh tokens of the other two sessions.
Expected Result: All three sessions are invalidated; resource server rejects the old tokens; the IdP emits a logout token to every client.
Security Implication: Compromised sessions must die everywhere, not just where the user clicked logout.
Test Data: 3 active sessions, same subject.
Cleanup: Re-authenticate test user for later tests.
Priority: High
Automation Possible: Yes - API
